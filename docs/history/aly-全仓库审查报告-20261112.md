#### B1. 服务端上传接口 projectName 未校验 → 路径穿越【已人工核实】
- 位置：`server/controllers/file_upload_controller.go:69, 173, 234`（三个上传入口都只检查 `len(projectName)==0`，均未调用已存在的 `validateProjectName`）
- 链条：`projectName=".."` 时 `GetProjectWorkPath`（经 `filepath.Join` Clean）得到 exeDir 本身 → 第 87 行的前缀校验反而变成"允许写服务器可执行文件目录"。`projectName="../.."` 可写整棵上级目录树。

> **【人工核实】成立，且比报告更严重**——`validateProjectName` 的正则 `^[^<>:"/\\|?*]{1,64}$` 本身**放行 `.` 和 `..`**（测试 `test/tc/cases_106_115_test.go` 注释自认可），因此报告原 P0 修复建议"补 validateProjectName 调用"**修不住本问题**。更优修复（三管齐下）：① `validateProjectName` 本体显式拒绝 `.`/`..`；② 三个上传入口补调用；③ `GetProjectWorkPath` 内做落位断言（Clean 后必须位于 data/ 之下）作纵深防御，兜住未来任何入口漏校验；④ TestCase110 从容忍式断言改为必须拒绝。
>
> **【再次审查】成立（细节修正）**——三入口行号精确（file_upload_controller.go:69/173/234，前置仅 len(projectName)==0），`..` → exeDir 且 :87 前缀校验反而放行，经 %TEMP% 路径矩阵实测复现。但两侧共用的例子 **"`../..` 可写整棵上级树"有误**：实测 `../..` → workDir=C:\（Clean 后），前缀校验反而拒绝一切普通落盘路径（唯一通过的是 `absFileName==workDir` 退化子句，仅短暂 .merging 写入后 rename 失败）。**真实穿越形状是 `"../<任意子路径>"`（单层 `..`）**——可达 exe 父目录及更上层整棵树，且 UploadFile/Chunk 的自动建目录（:76-81/:178-183）顺带实现"任意位置 mkdir"。正则对 `.`/`..`/`..data` 放行实测复现；TestCase110 的 `..` 子测试确为容忍式（cases_106_115_test.go:397-412 只记 Logf）。Linux 侧后果全额成立（deploy-server.go:22-23 root + /root/... 部署路径，覆盖二进制/aly.db、写 /root/.ssh/authorized_keys 均可达）；Windows 侧被运行中文件占用折扣（无 FILE_SHARE_DELETE）。
> **修复方案修正一处实现陷阱**：人工第①条"正则显式拒绝"不能实现为负向前瞻——Go regexp（RE2）**不支持 `(?!)`**；把 `.` 加进排除字符类会误杀 `a.b` 类合法名。正确姿势是正则校验后追加**精确等值判断**：`if name == "." || name == ".." { return err }`。②三入口补调用照做；③落位断言放 `GetProjectWorkPath`（service 层，避免 controllers→service 反向依赖）——workDir 与 dataDir 同源 `os.Executable()` 推导，合法名 Clean 后必然恰为 `dataDir\name`，**不会误伤合法路径**；④TestCase110 改必须拒绝并补 `"../sub"` 用例（覆盖修正后的真实穿越形状）。**P0，小时级**。

## 第二部分：技术架构问题与改进建议

### 2.1 值得肯定的设计（先说优点，避免误伤）
- **version.json 状态机 + 崩溃恢复**：downloaded/applying/applied + RollbackPrevious/ApplyStage/DownloadedFileCount/ApplyFailCount 的组合防御覆盖了大量真实事故场景，代码注释可追溯到历次回归（F1-F10、Bug#1-#6 等），防御性远超同类项目。
- **协议单一真源**：schema → alyprotocol 生成器（-write/-check 双模式可 CI 校验）→ fake-aly-client 场景回放，11 语言 SDK 场景下这是正确且成熟的工程路线。
- **subprocess + JSON 行协议**的 GUI/CLI 分层：Go CLI 天然跨平台交叉编译，C# GUI 只做编排，单人团队成本最低的正确选择；MVVM 纪律、AGENTS.md 规则执行良好。
- **SQLite（modernc.org/sqlite 纯 Go）选型**：单机低并发零运维场景典型正确，且支持直接交叉编译。

> **【人工核实】优点评价与代码观察一致，无异议。**
