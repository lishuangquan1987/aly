## 二、逐条详情与修改方案

### 2.1 #5 版本目录与实际内容错配（P1）

**结论：存在**，但报告给出的复现路径不精确。

**事实核对：**

- `apply_update.go:212` 用 `VersionPrevious` 命名备份目录，**该处是正确的**（apply 时 MainFolder 内容确实是 VersionPrevious 版本）。
- 真正出错的是 `rollback.go`：
  - `:60` `oldVersion := versionInfo.Version`
  - `:110` `prevVersionDir := fc.ExeCfg.AppVersionDir(oldVersion)`
  - 当 `version_status = downloaded` 时，`versionInfo.Version` 是**待应用的新版本**，而 MainFolder 里仍是旧内容 → 备份目录名与实际内容错配。
- 报告举例"V1 应用后下载 V2 再 rollback --version V1"要求 `ApplicationFolder_V1` 存在；但 V1 已在 MainFolder 中、该目录不存在，会被 `rollback.go:50` 的 `os.Stat` 拦截（"version not found"），**该例不可达**。
- **可达的错配路径**：V0 安装 → apply V1（留下 `ApplicationFolder_V0` 备份）→ 下载 V2（`ApplicationFolder_V2` 为待下载目录；version.json：`Version=V2, VersionPrevious=V1, downloaded`）→ `rollback --version V0`：
  1. `oldVersion = V2`，`prevVersionDir = ApplicationFolder_V2`（存在，是待下载目录）；
  2. `ApplicationFolder_V2` 被挪到 `.old`（待应用下载被旁移）；
  3. MainFolder（V1 内容）被改名成 `ApplicationFolder_V2` —— **错配**（V1 内容命名为 V2）；
  4. `ApplicationFolder_V0` → MainFolder；清理时删除 `.old` —— **待应用的 V2 下载丢失**；
  5. version.json 写成 `Version=V0, VersionPrevious=V2`（错误）。
  - 之后 `rollback --version V2` 会拿到 **V1** 的内容，静默错版本，无法自查。

**修改方案**（`client/aly-client`，Go 1.10 兼容）：

1. `rollback.go` 计算"当前 MainFolder 真实版本"用于备份命名与最终写入：
   ```go
   activeVersion := versionInfo.Version
   if versionInfo.VersionStatus == config.VersionStatusDownloaded && versionInfo.VersionPrevious != "" {
       activeVersion = versionInfo.VersionPrevious
   }
   ```
   将 `oldVersion`（`:60`）与 `prevVersionDir`（`:110`）改用它；最终写 version.json 时 `VersionPrevious = activeVersion`（`:178`）。
2. `rollback.go` 入口加守卫：`*versionFlag == versionInfo.Version && versionInfo.VersionStatus == config.VersionStatusDownloaded` 时拒绝（目标目录是未应用的下载目录，不可回滚）。
3. `list_rollback.go`：status=downloaded 时排除 `versionInfo.Version`（待应用目录不出现在回滚列表）；同时修正 `CurrentVersion` 此时应显示 `VersionPrevious` 的问题（`:52-55` 现在显示的是待应用版本）。
4. 报告建议的"自增序号 + manifest 维护目录名 ↔ 版本映射"列为可选增强（阶段 2），非本修复必需。

**边界：** 崩溃恢复分支（applying）不动；rollback 失败兜底（`launchMainExeFn`）保持。

**测试：** 新增 `rollback_test.go`：构造 downloaded 状态 + 两个版本目录，断言备份目录名=实际内容版本、待下载目录未被删除、version.json 的 Version/VersionPrevious 正确；守卫用例（回滚到未应用版本被拒）。

### 2.2 #6 check_update 与 download_update 版本判断口径不一致（P1）

**结论：存在。**

**事实核对：**

- `check_update.go:81` `if serverVersion == localVersion`（**相等判断**）→ 服务端版本低于本地时走 else 分支：`HasUpdate=true` 且携带 `ForceUpdate`；
- `download_update.go:82` `if compareVersion(newVersion, currentVersion) <= 0` → `"already at latest version"`（**大小判断**）；
- 后果：服务端回滚发布 / 服务端数据重建 / 连错环境时，`check_update` 说必须更新、`download_update` 说已是最新 → 开启强制更新的客户端**永久卡死**；
- `check_update.go:126`（pending 分支）同为相等判断，存在同类问题（server < pending 时误报"服务器有新版本"→ 重新下载，而 download 又报 already at latest → 循环报错）。

**修改方案**（`client/aly-client`）：

1. `checkUpdateApplied`（`:81`）改为大小判断：`needUpdate := compareVersion(serverVersion, localVersion) > 0`；不满足 → `HasUpdate=false`（死锁自动消除；服务端回滚/连错环境时客户端安静停在本地高版本）。
2. `checkUpdatePending`（`:126`）改为：`compareVersion(serverVersion, localVersion) <= 0` → 继续 apply 已下载版本（`NeedDownloadUpdate=false`）；`> 0` → 重新下载（把"相等"扩展为"不高于"，与 download 语义一致）。
3. SDK 侧 `AlyUpdateClient.cs` MainLoop：download 返回 NG"already at latest version"时视为正常无更新（`ClearError` + 继续轮询），避免错误刷屏。
4. 服务端 kill-switch / 降级出口（报告建议）列为可选：在 `SetForceUpdate` 之外提供按版本号取消强制更新的能力。

**测试：** check_update 三态用例（server>local / == / <）与 download_update 的 `compareVersion` 联合断言：server<local 时 check 无更新、download 不报错。

### 2.3 #7 服务端 get_all_files 全盘哈希 + 临时文件污染（P1）

**结论：存在。**

**事实核对：**

- `file_download_controller.go:50-95`：每次请求 `filepath.Walk(workDir)` 全目录，并对每个文件实时计算 MD5+SHA256（`:77-84`），无缓存、无 ETag、无版本快照；
- `file_upload_controller.go:147` 分片暂存目录 `xxx.dll.chunks/`、`:240` 合并临时文件 `xxx.dll.merging` 都在 workDir 内，会被 Walk 扫出并作为正式文件返回 → 上传进行中任何客户端 check 都会看到幽灵文件、哈希不匹配并尝试下载。

**修改方案**（`server/`，Go 1.25）分两阶段：

- **阶段 1（止血，最小改动）**：
  1. `GetAllFilesByProjectName` Walk 中跳过 `*.chunks/`、`*.merging`、`*.part`、`*.tmp`（目录与文件两级都判断）；
  2. `DownloadFile`（`:135`）对路径含 `.chunks` / `.merging` 的直接 404（纵深防御）；
  3. 可选：内存 TTL 缓存（key=projectName，TTL 30s 或基于目录 mtime），先缓解客户端轮询压力。
- **阶段 2（推荐，与报告路线图第 2 条一致，一并解决 #4 删除文件能力）**：
  1. 新增 ent schema `FileMeta`（project_id, version, rel_path, size, md5, sha256，唯一索引 `(project_id, version, rel_path)`）；
  2. `publish_version` 时生成不可变清单写入 DB；`get_all_files` 改为按最新版本读 DB 返回，不再 Walk + 哈希；
  3. 客户端下载改用相对路径拼 URL（顺带解决 #15 FileAbsolutePath 泄露与 #16 IDOR 越权）；
  4. apply 按 manifest 重建目标目录（与 #4 删除文件联动，见报告）。

**边界：** UploadChunkComplete 合并完成后需同步/失效清单；上传过程中的并发请求读到旧清单可接受。

**测试：** 上传一个分片中间态 → get_all_files 不返回该临时文件；两次请求结果一致；清单模式下删除文件后客户端能看到删除集。

### 2.4 #8 更新器自更新（P2，报告机制判断有误）

**结论：部分成立。报告核心论断（"目标 UpdatorExePath 正是当前正在运行的那个 exe → 永远失败"）不成立。**

**事实核对：**

- `AlyUpdateClient.cs:47-67`：目标 `UpdatorExePath` 默认 `BaseDirectory\..\UpdateFolder\aly-client.exe`（宿主在 ApplicationFolder，更新器在 UpdateFolder，**二者不同进程**）；
- `CheckSelfUpdateAsync(UpdatorExePath).Result`（`:56`）同步等待子进程退出后才执行 `File.Copy`（`:61-62`），目标此时**未被占用**；
- `deploy-client.go:108-119` 会把 aly-client.exe 同时部署到项目目录（随发布包下发，即复制源）与 `../UpdateFolder`（复制目标）——源文件存在、复制方向正确；
- 结论：正常流程下自更新**可以成功**，报告"永远失败"的判断不成立。

**真实缺陷（值得修）：**

1. `catch (Exception) { }`（`:64`）静默吞掉一切异常，无日志（违反"不留痕"要求）；
2. `File.Copy` 非原子：中途崩溃留下损坏的 `UpdateFolder/aly-client.exe`，后续所有更新不可用；
3. 竞态窗口：宿主被 apply_update 重启的瞬间，旧更新器进程可能尚未完全退出 → 目标被占用 → 复制失败被吞（下次启动可自愈，但无日志难排查）；
4. 复制前未校验源/目标完整性（SHA256）。

**修改方案**（`client/aly-client-sdk`，C# 5 / net40 兼容）：

1. 复制改为"临时文件 + SHA256 校验 + 原子替换"：copy 到 `UpdatorExePath + ".new"` → 比对源 SHA256 → `File.Replace`（net40 可用）；目标占用时重试 3 次、间隔 1s；
2. `catch` 内写日志（`%LocalAppData%` 或 EventLog），并通过 `ErrorStatusChanged` 上报，不再静默；
3. 失败不清空目标（保留旧更新器），下次启动重试。

**测试：** SDK 单元测试（目标被占用 → 重试成功/失败路径；复制中断 → 旧文件保留）；手工验证一次真实自更新。

### 2.5 #9 更新锁陈旧检测只看 PID（P2）

**结论：存在。**

**事实核对：**

- `lock.go:59` 写入了 `TS`（`time.Now().Format("2006-01-02 15:04:05")`），但 `:71-88` `cleanStaleLock` **只查 `IsProcessAlive(PID)`，TS 从未读取**；
- `process.go:155-172` `IsProcessAlive` 对权限不足**保守返回 true**（ERROR_ACCESS_DENIED / 其他错误）→ 权限受限场景锁更易"永久有效"；
- 后果：持有者崩溃 + PID 被复用（或权限不足）→ 锁永远有效，所有更新卡死，只能手工删 `.aly.lock`。

**修改方案**（`client/aly-client`）：

1. `cleanStaleLock` 增加 TTL：读取 TS，超过 **30 分钟**无条件删除抢占；TS 解析失败按陈旧处理；新写入的 TS 改用 Unix 秒数字符串（兼容解析旧格式"2006-01-02 15:04:05"，Go 1.10 `time.Parse` 可用）；
2. 锁内容增加随机 token（如 `pid-unixnano`），释放时先读文件校验 token 再 `os.Remove`，避免误删新持有者的锁；
3. `tryAcquireLock` 写入失败（如残留空文件）也走 cleanStaleLock 重试。

**测试：** `lock_test.go` 增补：陈旧锁（PID 不存在）清理；TTL 内不抢占、超 TTL 抢占；token 不匹配不删锁。

### 2.7 #11 runScript 异步 Wait（P2）

**结论：存在**，程度略轻于报告表述。

**事实核对：**

- `common.go:430-444`：`cmd.Start()` 后 `go func() { cmd.Wait(); ...日志 }()`；
- `cmd /c` 脚本进程在父进程退出后仍会跑完（Windows 语义），所以**脚本本身不中断**；实际丢失的是 `cmd.Wait()` 的结果日志——apply_update 的 `main()` 返回后进程退出，goroutine 被杀；
- 且脚本与主程序启动无先后保证（`runScript` 在 `launchMainExe` 之前调用，但脚本是异步的）。

**修改方案**（`client/aly-client`）：

1. `runScript` 改为同步执行 + 超时：`cmd.Run()` + 60s 超时（超时 TerminateProcess），结果写入 update.log；
2. 调用顺序二选一（需与业务确认脚本语义）：
   - **默认推荐**：`launchMainExe` 之后同步执行（先保证主程序可用，再跑后置脚本，同时不丢日志）；
   - 若脚本必须先于主程序（清理/准备类）：launch 前同步执行 + 超时。
3. 脚本不存在（`:413` 已处理）行为保持；脚本挂死由超时兜底。

**测试：** `runScript` 单测（脚本执行并写日志；超时被杀）。

### 2.9 #13 强杀 explorer 与无关进程（P2）—— 已按用户决定修订

**结论：存在。**

**事实核对：**

- `common.go:306-325` `closeExplorerWindows` 杀**所有** explorer.exe（先 WM_CLOSE 后强杀，Explorer 自动重启）；
- `common.go:194-220` `closeProcessesHoldingFolder` 强杀**任何持有目录句柄的进程**（记事本、IDE、杀软等无关进程均可能）；
- `renameDirWithKill` / `renameWithKillRetry`（`:231-302`）在重试失败时同样触发强杀 / `closeExplorerWindows` 兜底。

**用户决定（已确认）**：explorer 占用导致重命名不成功时，**杀掉 explorer 是正确且应保留的补救手段**。本次修改**不动 explorer 处理逻辑**，只修"无关进程"被强杀的问题。

**修改方案**（`client/aly-client`）：

1. **保留** `closeExplorerWindows`（`common.go:306-325`）现状：重命名失败且 Restart Manager 探测不到占用者（典型：Explorer 文件夹窗口持有目录句柄，RM 检测不到）时，关闭并结束 explorer（系统自动重启）——预期补救，不改、不加开关；
2. `closeProcessesHoldingFolder`（`common.go:194-220`）改为**白名单强杀**：
   - 白名单 = `must_close_process_name` + 主程序 exe 名 + `explorer`；
   - 白名单进程：保持现有 WM_CLOSE 优雅关闭 → 超时强杀；
   - 非白名单持有者（记事本、IDE、杀毒等无关进程）：**不强杀**，发 WM_CLOSE 优雅尝试后收集进程名，返回错误"以下进程占用更新目录，请关闭后重试：xxx"；该错误沿 `applyReplacement` 返回，经 `applyFailureFallback` 启动旧版本主程序并把错误带给用户（SDK 界面展示）；
3. `renameWithKillRetry` / `renameDirWithKill` 内 `findHoldersOf` 的强杀路径同样套用白名单；找不到占用者时仍走 `closeExplorerWindows` 兜底（保留）；
4. 可选增强（不阻塞主方案）：`closeExplorerWindows` 尽量只关闭"当前目录 == 目标目录"的 Explorer 窗口（XP/386 下经 Shell.Application COM，若实现成本可接受），避免误关用户其他资源管理器窗口；不可行则维持现状并在 README 说明；
5. README 记录该行为与"无人值守 / 交互式部署"的配置建议。

**边界：** `must_close_process_name` 未配置时白名单退化为 `主程序 exe + explorer`；强杀后的进程退出等待逻辑（`ForceKillPIDs`）保持。

### 2.10 #14 上传大小限制时机太晚（P2）

**结论：存在。**

**事实核对：**

- `file_upload_controller.go:22-32`：`ctx.FormFile("file")` 触发 Gin `ParseMultipartForm`（默认 32MB 内存阈值，超出部分落盘到系统临时目录）**之后**才检查 `f.Size`；
- 未设 `MaxBytesReader` / `MaxMultipartMemory` → 1GB 文件先写临时盘再拒绝（注释"multipart 解析时即校验"与实际不符）；
- `UploadChunk`（`:115-124`）同样问题；合并累计校验在 `:224`（已存在，保留）。

**修改方案**（`server/`，Go 1.25）：

1. `UploadFile` / `UploadChunk` 入口先设置 `ctx.Request.Body = http.MaxBytesReader(ctx.Writer, ctx.Request.Body, maxUploadFileSize+1MB)`（预留 multipart 边界开销），超限后返回 413；
2. 早读 `Content-Length` 头，超过上限直接 NG（不解析 body）；
3. 路由初始化处设置 `r.MaxMultipartMemory = 8 << 20`；
4. 捕获 `http.MaxBytesError`（Go 1.19+）返回友好错误。

**边界：** 分片接口单分片上限独立设置（避免单分片 1GB 的极端值）；合并累计校验保留。

**测试：** 超限文件上传 → 413/NG 且不残留临时文件；分片合并累计超限 → 拒绝。

## 三、"四、附"三个核对点审核

### 3.1 ShouldSkipFolder 用 filepath.Match，无法表达任意深度嵌套 —— 属实

**核对：**

- `config.go:162` `filepath.Match(pattern, relPath)`：`*` 不跨 `/`，`**/node_modules` 只匹配一层（`a/node_modules`），不匹配 `a/b/node_modules`；
- 现有 `config_test.go:16` 用例（`"src/node_modules"` + `"**/node_modules"`）恰好只覆盖一层，未暴露该限制；
- 另发现**三处忽略实现不一致**：
  - 客户端 `config.ShouldSkipFolder`（glob + EqualFold 精确）；
  - 服务端 `file_download_controller.go:65-69`（`strings.HasPrefix` 前缀）；
  - publish-cli `scanner.go:46-50`（`isSubPath` 前缀）。
  - 简单名称（如 `logs`）三处行为接近，但 glob 模式与嵌套语义存在差异，同一 `ignore_folders` 配置在"发布扫描 / 服务端列表 / 客户端复制"三个环节可能行为不同。

**修改方案：**

1. 客户端自实现一个支持 `**` 递归的匹配函数（Go 1.10、GOPATH 模式不宜引第三方库，约 30-40 行），保留 EqualFold 精确匹配；
2. 三处实现统一"忽略文件夹"的匹配规则与文档（至少统一语义并补充测试）；
3. 测试增加多层嵌套用例（`a/b/node_modules`）。

### 3.2 matchIgnoreFile 中 pattern 为 "*" 时忽略全部文件 —— 属实，且为有意设计

**核对：**

- `file_download_controller.go:114-133`：`"*"` 时 `strings.HasPrefix(pattern, "*")` → `strings.HasSuffix(relPath, "")` 恒真 → 忽略全部文件；注释（`:112-113`）声明"有意设计"，语义接近 .gitignore 的 `*`；
- 与 publish-cli `scanner.go:258-289` `matchFile` 的 `*` 后缀分支行为一致；
- 审核结论：行为跨端一致、符合注释意图，风险仅是**误配**（把 `*.log` 写成 `*`）。

**修改方案：** 在 publish-gui / publish-cli 校验 `ignore_files` 时对 `"*"` 给出显式警告；README 记录该语义；**不改默认行为**。

### 3.3 check_diff.go 并发写 diffFiles[idx].LocalSHA256 —— 属实，但不构成 data race

**核对：**

- `check_diff.go:99-111`：每个 goroutine 写 `diffFiles[idx].LocalSHA256`，idx 为不同索引 → 不同内存地址，**技术上不构成 data race**；
- 切片在并发前已构建完毕（`:64-95`），并发期间无 append → 当前安全；
- 风险仅在将来有人误加 `append(diffFiles, ...)`。

**修改方案：**

1. 加注释锁定约束（"并发阶段只允许按下标写，禁止 append / 扩容"）；
2. 或顺手改为结果数组回填（`results[i] = sha256` 后再合并，更稳，改动小）。
