# Aly 桌面端自动更新方案 —— 代码分析与对比

> 分析对象：`lishuangquan1987/aly`（master 分支）
> 模块：`server/`（Go + Gin + Ent + SQLite）、`publish/publish-cli`（Go + cobra）、`publish/publish-gui`（Avalonia/.NET 8）、`client/aly-client`（Go 1.10，Windows）、`client/aly-client-sdk`（C#）
> 审阅重点：更新原子性、崩溃恢复、服务端安全、与主流方案的差距

---

## 一句话结论

**架构选型是对的**（三层目录 + 独立更新器 + 状态机 + 原子替换），作者明显踩过 Windows 替换文件的坑并留下了高质量的防御代码；但**服务端是"裸奔"的**（无鉴权、任意路径写、无签名），而且**"删除文件"这个能力在整条链路上缺失**。做内网可信环境的轻量方案可以，一旦放到公网或多客户端规模，P0 级问题会先爆。

---

## 一、Bug 清单（按严重度）

### P0 — 必须修，否则可被利用或直接不可用

#### 1. 服务端零鉴权 + 项目名未校验 = 任意文件写入 / 供应链投毒

`routers/routers.go` 里 **所有 API 都没有任何认证**：谁都能 `POST /api/file/upload_file`、`POST /api/project/publish_version`。

更严重的是 `internal/service/project_service.go:29`：

```go
func GetProjectWorkPath(projectName string) (string, error) {
    exe, _ := os.Executable()
    dir := filepath.Dir(exe)
    return path.Combine(dir, DataDirName, projectName), nil   // projectName 未做任何校验
}
```

`file_upload_controller.go:68-73` 的校验逻辑：

```go
absFileName := filepath.Clean(path.Combine(workDir, fileName))
if !strings.HasPrefix(absFileName, workDir+string(filepath.Separator)) && absFileName != workDir {
    return NG("非法的文件路径")
}
```

**前缀校验的基准 `workDir` 本身就是被污染的路径** —— 项目名传 `..\..\..\Windows\Temp\x`，`filepath.Clean` 归一化后逃逸出 `data/`，而 `absFileName` 仍然以 `workDir` 开头，检查照样通过。**后果**：一次 POST 就能让所有客户端下次更新时被植入恶意 exe/dll。

修复：
- 项目名限定 `[A-Za-z0-9_.-]` 白名单（长度也限制）
- 用**绝对化的 dataRoot**（而非被污染的 workDir）做 `filepath.Rel` 校验，且要求 `!strings.Contains(rel, "..")`
- 写接口全部加 Token；发布证书用短期凭据

#### 2. 没有签名机制，哈希值与文件来自同一条不可信通道

客户端 `download_update.go:182` 的校验：

```go
if localMD5 == dl.serverFile.MD5 && localSHA256 == dl.serverFile.SHA256 { break }
```

而 `serverFile.MD5 / SHA256` 是 `api/file/get_all_files` 响应里一并返回的。**同一个响应里的哈希和被哈希的文件，在不可信通道上不构成任何信任**。README 示例全是 `http://localhost:2000`，MITM 改内容同时改哈希即可完全绕过。更新落地后也**没有检查 Windows Authenticode 签名**。

对比：Velopack/Squirrel 强制 nupkg 签名、Sparkle 2 强制 EdDSA 签名 appcast、ClickOnce 强制清单签名 —— 这是本项目与主流方案差距最大的一项。

修复（最小可行）：发布端用 Ed25519 私钥对整个文件清单签名生成 `manifest.sig`，客户端内置公钥验签，验证通过后再下载文件。

#### 3. 客户端未校验服务端返回的路径（Zip-Slip 类）

`download_update.go:46`：

```go
localPath := filepath.Join(targetDir, filepathFromSlash(relPath))
```

`relPath` 完全来自服务端响应，无任何校验。返回 `..\..\..\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\x.exe` 即可写到任意位置。与第 1、2 条串起来就是完整的远程代码执行链。

修复：`filepath.Clean` 后强制 `strings.HasPrefix(abs, targetDir+string(os.PathSeparator))`，并拒绝绝对路径 / 盘符 / UNC。

### P1 — 会真实踩到的功能缺陷

#### 4. 文件永远无法删除

`diff/scanner.go:183` 能算出 `"deleted"` 状态，但：
- push 链路**不删除**服务端文件（`internal/cmd/push.go` 全文无删除逻辑）
- apply 链路是 `CopyDirWithExclude(MainFolder → versionDir)` 的**复制-覆盖**语义，且 `CopyFile(..., overwrite=false)`，**已废弃的旧文件会被原样带进新版本**

后果：改名拆分的 dll、卸载残留的库、多年前的旧 exe 会无限累积在 `ApplicationFolder/` 里。加载器可能误命中残留的旧版本程序集 —— 这类问题在上位机/工控场景排查起来极其痛苦。

修复方向（同时也是性能解）：把"版本"做成**不可变快照 + manifest**，apply 时按 manifest 重建目标目录，而不是把旧目录复制过去。

#### 5. 版本目录与实际内容可能错配（rollback 路径）

`apply_update.go:212` 用 `VersionPrevious` 命名备份目录，写入的却是**当前 MainFolder 的实际内容**：

```go
prevVersionDir, _ := fc.ExeCfg.AppVersionDir(versionInfo.VersionPrevious)
...
renameDirWithKill(fc.MainFolder, prevVersionDir, closeTimeout)
```

正常路径没问题 —— `download_update.go:201` 会把 `VersionPrevious = 当前 Version`，两者一致。但下面这条路径会错配：

> V1 → 下载 V2 完成（json: `Version=V2, VersionPrevious=V1`, status=`downloaded`）→ 此时执行 `rollback --version V1`

此时 `oldVersion = V2`，`prevVersionDir = ApplicationFolder_V2`，而 MainFolder 里其实是 **V1** 的内容 → 被 rename 成 `ApplicationFolder_V2`。此后 `rollback --version V2` 拿到的是 V1 的东西。静默错版本，无法自查。

修复：备份目录名取**替换前 MainFolder 的真实版本**（`versionInfo.Version`，rollback 后已更新为实际值），而非 `VersionPrevious`；或用自增序号命名，在 manifest 里维护 `目录名 ↔ 版本` 映射。

#### 6. check_update 与 download_update 版本判断口径不一致 → 强制更新死锁

| 位置 | 判断方式 |
|---|---|
| `check_update.go:83` | `serverVersion != localVersion`（**相等比较**） |
| `download_update.go:82` | `compareVersion(newVersion, currentVersion) <= 0`（**大小比较**） |

服务端版本低于本地时（回滚了发布 / 服务端数据重建 / 连错环境）：

- `check_update` → `HasUpdate=true, ForceUpdate=true`
- `download_update` → `"already at latest version"`

开启了强制更新的客户端会**永久卡在"必须更新"却永远更新不了**的状态，应用不可用。

修复：两处统一语义 `needUpdate = compareVersion(server, local) > 0`；`force_update` 必须有降级/跳过出口，并在服务端提供 kill-switch。

#### 7. 服务端 get_all_files 每次全盘哈希 + 临时文件污染 → 随规模雪崩

`GetAllFilesByProjectName` 对每个请求遍历整个项目目录，**对每个文件实时计算 MD5 + SHA256**（`file_download_controller.go:77-84`），无缓存、无 ETag、无版本快照。100 台客户端、500MB 项目、每分钟轮询一次 —— 服务端 IO 直接打满。

更麻烦的是**中间态文件会被当成正式文件返回**。分片上传的暂存目录就在 workDir 里：

```go
chunksDir := absFileName + ".chunks"      // file_upload_controller.go:147
mergePath := absFileName + ".merging"     // :240
```

`filepath.Walk(workDir)` 会把 `xxx.dll.chunks/0,1,2…`、`.merging` 全部扫出来返回给客户端。上传进行中时，任何触发 check 的客户端都会看到这些幽灵文件、哈希不匹配、然后去下载它们。

修复：
- Walk 时排除 `*.chunks/`、`*.merging`、`*.part`
- **哈希在 push 时算一次写进 DB**，`get_all_files` 只读 DB
- 加 ETag / 基于发布版本号的 304

#### 8. 更新器自更新实际不生效

`AlyUpdateClient.cs:57`：

```csharp
File.Copy(Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "aly-client.exe"),
          UpdatorExePath, true);
} catch (Exception) { }
```

目标 `UpdatorExePath` 正是**当前正在运行的那个 exe**。Windows 不允许覆盖正在执行的映像 → `IOException` → 被空的 `catch` 静默吞掉。自更新永远失败且不留痕。

修复：先把自身 rename 成 `aly-client.exe.old`，再 Copy，下次启动清理；或用独立 bootstrapper 进程。

### P2 — 健壮性 / 体验

| # | 问题 | 位置 | 说明 |
|---|---|---|---|
| 9 | 更新锁陈旧检测只看 PID，`TS` 字段写了从不读 | `lock.go` | 持有者崩溃 + PID 被复用 → 锁永久"有效"，所有更新卡死需手工删 `.aly.lock`。应加 TTL（>30min 无条件抢占） |
| 10 | `launchMainExe` 未设置子进程工作目录 | `common.go:369` | `exec.Command(exePath)` 的 `Dir` 为空 → CWD 继承调用方（很可能是 UpdateFolder）。主程序用相对路径读配置会读错目录。应显式 `cmd.Dir = fc.MainFolder` |
| 11 | `runScript` 用 goroutine 异步 Wait | `common.go:431` | 主进程随即退出，goroutine 被杀，后置脚本日志丢失；且脚本没跑完就已启动主程序 |
| 12 | `LocalFileMD5Map` 硬编码排除 `"update"` 目录 | `util/file.go:129` | README 里该目录叫 `UpdateFolder`，命名不一致导致排除失效。应改为排除 `config.ExeDir()` 而非猜名字 |
| 13 | 强杀 explorer 与无关进程 | `common.go:306` | `closeExplorerWindows` 杀掉**所有** explorer.exe —— 用户的资源管理器窗口、桌面壳、正在进行的复制/粘贴全部中断。`closeProcessesHoldingFolder` 同样会强杀持有句柄的无关程序（记事本打开的日志、IDE、杀毒扫描）。建议只对 `must_close_process_name` 强杀，其余提示用户手动关闭后重试 |
| 14 | 上传大小限制时机太晚 | `file_upload_controller.go:29` | `f.Size` 检查发生在 multipart 已落盘之后，且未设 `MaxBytesReader` / `MaxMultipartMemory`，1GB 文件先写临时盘再拒绝 |
| 15 | `FileAbsolutePath` 泄露服务端绝对路径 | `file_download_controller.go:87` | 应下发ID/相对路径；客户端据此拼 URL 也耦合了服务端文件系统布局 |
| 16 | `DownloadFile` 不校验项目归属 | `file_download_controller.go:135` | 只校验在 `data` 目录内 —— 任意项目的客户端可下载其他项目全部文件（IDOR 越权读取）。结合 #15 泄露的绝对路径，跨项目读取直接成立 |

## 二、与主流开源方案对比

### 参照系

| 方案 | 定位 |
|---|---|
| **Squirrel.Windows / Velopack** | .NET/Windows 事实标准，Squirrel 的活跃继承者 |
| **ClickOnce** | .NET 内置，需部署清单 + 签名证书 |
| **WinSparkle / Sparkle** | macOS Sparkle 的 Windows 移植 / macOS 标准 |
| **Electron-updater** | Electron 生态，差量 + 灰度 + 多通道 |
| **Omaha (Google Update)** | 企业级，最完善也最重 |
| **MSIX / App Installer** | Windows 官方打包分发 |

### A 值得保留、做对了的地方

1. **三层目录布局**：`PackageFolder/{ApplicationFolder, UpdateFolder, ApplicationFolder_Vx}`。更新器及其状态文件（`version.json` / `client.json`）**不在**主程序目录内 —— 所以主目录可以被整体 rename 而更新器状态不受影响。这与 Squirrel 的 `app-x.y.z / packages / Update.exe` 布局同构，是这个方案能做原子替换的前提。**这是最关键的一个正确决策。**

2. **三重替身的原子替换**（`applyReplacement`）：旧备份先旁移 → 主目录改名为备份 → 新版本改名为主目录 → 清理。并且作者发现了 `MoveFileEx` 无法覆盖非空目录、Windows 上 Access denied 的实际表现，做了针对性处理。**这些注释是真实踩坑的沉淀，含金量高于代码本身。**

3. **状态机 + 崩溃恢复**：`downloaded → applying → applied`，且 `version.json` 用 tmp+rename 原子写；`applying` 状态能在下次启动时被识别并修复（还区分了"versionDir 还在/已不在"两种崩溃点）。**Squirrel 也没有这样显式的 applying 状态**，这块 Aly 做得更细。

4. **传输完整性基础件齐全**：MD5 + SHA256 双校验、>100MB 走 Range 断点续传、`.part` + rename 原子落盘、分片上传、MoveFile 前后均与 size 比对。缺的只是"信任根"（签名），见 P0-2。

5. **零常驻、零服务**：一个 exe + 多次 `Process.Start`，无需 Windows 服务、无需管理员权限（前提是装在有写权限的目录）。相比 Omaha/ClickOnce 的部署复杂度，学习成本极低。

6. **发布端 CLI + GUI 双形态**：`publish-cli` + Avalonia 跨平台 GUI —— 非技术同事能发布。这是 Squirrel、ClickOnce CLI 都没有的优势。

7. **文件级去重**：靠本地 MD5 比对跳过未变文件，虽然没有二进制差量，但复用率高、实现简单，对"只改几个 dll"的日常发版已经省不少流量。

### B 明显落后、建议优先补齐的差距

| 维度 | Aly 现状 | 主流做法 | 优先级 |
|---|---|---|---|
| **更新包签名** | 无；哈希与文件同源 | Velopack 签名 nupkg；Sparkle 2 强制 EdDSA；ClickOnce 强制清单签名 | **P0** |
| **服务端鉴权** | 全匿名，写接口裸奔 | Token / 短期签名 URL / CDN 回源鉴权 | **P0** |
| **更新包不可变** | `data/{project}/` 就是"最新版"，push 直接覆盖 → 更新过程中的多个客户端会读到**不一致的文件混合** | Squirrel/Velopack 的 `packages/` 保留每版本不可变 nupkg，`RELEASES` 清单定版 | **P1** |
| **删除文件能力** | 整链路缺失（见 #4） | 版本 = 完整快照，天然支持 | **P1** |
| **服务端性能** | 每请求全盘哈希 | 清单快照 + CDN + ETag/304 | **P1** |
| **二进制差量** | 仅文件级去重 | bsdiff DELTA 包（Velopack/Squirrel/Electron-updater），大版本省 70~90% 流量 | P2 |
| **历史版本保留** | 仅上一版本 | Squirrel 保留全部历史，可任意回滚 | P2 |
| **灰度 / 分批 / 回滚开关** | 无 | Omaha、Electron-updater 支持 staged rollout + kill switch | P2 |
| **per-user 安装（免 UAC）** | 只能靠部署目录有写权限 | Squirrel/Velopack/MSIX 支持装到 `%LocalAppData%` | P2 |
| **免打扰 / 后台静默安装** | 需自行实现 | Velopack `--silent`、ClickOnce 可选 | P3 |

## 三、改进路线建议（按性价比排序）

1. **先补信任根**（P0-1/2/3）：服务端写接口 Token 鉴权 → 项目名白名单 + dataRoot 绝对校验 → 客户端 manifest Ed25519 验签 → 客户端路径穿越校验。这一步做完，方案才谈得上"可用"。
2. **把"版本"改成不可变快照**：push 时生成 manifest（含哈希 + 删除集）写入 DB，`get_all_files` 读 DB 而非 Walk；apply 按 manifest 重建目录。一次性解决 #4/#7，并为差量更新铺路。
3. **统一版本比较语义**，给 force_update 加逃生出口（#6）。
4. **修自更新**（#8）与工作目录（#10）—— 这两个都会让"看起来能用"变成"其实没生效"。
5. 有余力再补：bsdiff 差量、多版本保留、灰度、per-user 安装。

## 四、附：不易发现但建议核对的点

- `ShouldSkipFolder` 用 `filepath.Match(pattern, relPath)` —— `filepath.Match` 的 `*` **不匹配路径分隔符**，所以 `ignore_folders` 无法表达嵌套规则（如 `**/logs`）。建议改用 `doublestar` 库。
- `matchIgnoreFile` 中 pattern 为 `"*"` 时会 `strings.HasSuffix(relPath, "")` 恒为 true → 忽略全部文件。注释称是"有意设计"，但这个坑太容易踩，建议显式警告或拒绝。
- `check_diff.go` 中对 `diffFiles[idx].LocalSHA256` 的并发写操作对象是不同内存地址的元素，技术上不构成 data race，但一旦将来有人加了 `append` 就会出问题，建议加注释锁定约束。
