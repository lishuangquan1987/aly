# aly 精简优化计划（2026-10-29 v2）

> 取代《aly-修复优化计划-20261029.md》（保留作参考，暂不执行）。
> 原则：**aly 是一个简单易用的局域网更新程序，不是要对抗恶意互联网的金融系统。**

---

## 一、对上一版计划的复盘

你的直觉是对的，上一版犯了三个错误：

1. **解决了你没遇到的问题**。签名链、TOFU、密钥管理是为"公网敌对环境"设计的。aly 的场景是局域网 + 自己人发布（OTDR 上位机），威胁模型弱得多。
2. **为"通用标准"牺牲了"简单"**。manifest/兼容矩阵/双轨灰度这些是为"被无数陌生项目采用"做的准备，但学习成本立刻转嫁到了你自己和用户身上——与"简单好用"的目标直接矛盾。
3. **两个"严重"定性不准确**（重读代码后确认）：
   - "推送中途客户端拿到混合内容"——实际被现有顺序防住了：push 先传完文件再建版本记录，download 有版本闸门，推送中客户端只会看到"无更新"。**此风险基本不成立**；
   - "apply 全量复制"——`CopyFile(overwrite=false)` 已有跳过语义，apply 实际只拷未变化文件。问题只是拷贝**发生的时机**（关进程后），挪个位置即可，不需要一个"物化工作流"。

结论：**现有架构（check→download→apply + 目录 rename + 状态机）是健康的，不需要推倒什么，只需要 8 件小改动。**

## 二、保留的 8 件事（按价值/成本排序）

### 1. UI：按钮卡片替代模态框（最高用户价值）

- 现状 `AskYesNo` 模态框打断用户（OTDR 全屏场景尤其烦）；
- 改为卡片上直接画 [立即更新] [稍后] 按钮，点击即走、不抢焦点；
- `i18n` 的 KeyRetry/KeyLater/KeyApply 等键已定义未用，正好启用。
- 改动：`view/card.go`（按钮绘制+热区）、`view/window.go`（WaitButton）、`app/run.go`（换调用）。
- 验收：更新询问全程无模态框、全屏主程序输入不被打断。

### 2. UI：失败重试按钮 + 错误人话化

- 失败态卡片加 [重试] [关闭]；重试=重跑当前阶段；
- 错误映射 10 条起步：sharing violation →"文件被占用，已尝试自动关闭占用程序"等。
- 改动：`app/run.go`、`i18n/*`。
- 验收：下载失败点重试可恢复；错误文案非原始英文技术串。

### 3. UI：强制更新倒计时 + 下载暂停

- 强制更新：显示"10 秒后自动重启"，可提前点，不倒计时直接干（现在的行为）太粗暴；
- 暂停：bridge 层已有 ctx cancel，杀 download 子进程即可；已完成文件自动保留（.part 机制已具备），继续=断点续传。
- 改动：`app/run.go`、`view/card.go`（SetCountdown）。
- 验收：倒计时准、可提前触发；暂停→继续 0 重传。

### 4. 下载：字节级进度（协议只增不改）

- `DownloadProgress` 增加 `downloaded_bytes/total_bytes/speed_bps`（omitempty，旧 SDK 无感）；
- UI 显示 `156MB/230MB · 2.4MB/s`，进度条按字节百分比——大包时"3/57 个文件"毫无信息量。
- 改动：`cmd/download_update.go`（统计）、`cmd/common.go`、`model/dto.go`、`bridge/parse.go`、`view/card.go`。
- 验收：字节数与实际落盘误差 <5%。

### 5. apply：把复制从 apply 挪到 download 尾部（小改动大收益）

- 现状：download 只下差异 → apply 时（进程已关）才把未变化文件从 MainFolder 拷进版本目录 → 关进程窗口=复制全程，GB 级目录以分钟计；
- 改法：**download 结束时就把未变化文件拷齐**（主程序还在运行，只读复制无害），apply 只剩三次 rename，关进程窗口秒级；
- 拷贝沿用现有 `CopyDirWithExclude`（已具备跳过语义），只是换个调用位置+补一个崩溃残留用例（现有 B2 自愈逻辑天然覆盖）。
- 改动：`cmd/download_update.go` 尾部 +1 段调用；`cmd/apply_update.go` 移除复制（legacy 无 manifest 场景行为不变？——本计划不做 manifest，因此 apply 对"目录已齐"的场景自然短路：CopyDir 全部跳过，成本为零，**apply 侧甚至可以不改**，复制留作兜底）。
- 验收：1GB 目录 3 文件差异，从关进程到新版本就位 ≤10 秒。

### 6. download：单文件失败不整体失败

- 现状：某文件 3 次重试失败 → 整个 download 失败，宿主整体重来；
- 改法：记录失败清单，全部跑完再统一输出 FAIL + `failed_files`；重试只重失败文件（断点续传天然支持）。
- 改动：`cmd/download_update.go` 循环结构小调。
- 验收：注入单文件失败，其余文件照常下载，失败清单准确。

### 7. clean 命令（独立清理入口）

- 现状 prune 只在 apply/rollback 入口机会式触发，客户端不再更新就永远占盘；
- 把 `pruneVersionSnapshots` 提为独立命令 `aly-client clean [--keep N] [--all]`，顺带清 `.old*`、`.part/.tmp`、超 30 天的失败日志。
- 改动：`cmd/prune.go` → `cmd/clean.go`（搬运）+ `main.go` 注册。
- 验收：`clean --all` 后只剩 MainFolder+运行件，回收量日志可核对。

### 8. 两个小修复

- **semver 比较**：`compareVersion` 不认 `1.0.0-beta`（解析成 0，排序错）。改为 semver 感知（预发布<正式版），纯数字旧格式行为不变。+30 组排序单测。
- **服务端防倒退**：`PublishVersion` 校验新版本必须严格大于最新版本，否则拒绝（防手滑；确需回退走例外 flag）。重发同版本号导致的"客户端卡旧内容"问题由此根治（这是 D1 里唯一真实且值得修的点）。

## 三、明确砍掉的（及捡回信号）

| 砍掉 | 为什么 | 什么信号出现再捡回 |
|---|---|---|
| Manifest 清单/冻结版本 | 你没有"版本漂移"的实际痛点；现有"可变引用"反而免费提供了自愈（文件被改会自动重下） | 出现多人并发发布/需要并行多版本时 |
| 签名链/TOFU/密钥 | 局域网+自己人发布的威胁模型不需要；学习成本高 | 更新程序要暴露公网时 |
| carry_over 语义反转 | 一次性迁移成本，收益（删除语义）暂时不痛 | 目录膨胀真成问题时（先靠 clean 顶着） |
| 删除下发 | 无 manifest 时实现别扭；膨胀问题 clean 已缓解 | 同上 |
| verify 命令 | **已有等价物**：`check_diff` 就是"本地 vs 服务端全量比对" | — |
| 差分/渠道/静态服务器/多应用 | 研究性方向，与"简单"矛盾 | 有真实需求单独立项 |
| 兼容矩阵/双轨灰度 | 本计划不新增服务端 API、协议只增字段——新旧天然互兼容，无需矩阵 | — |
| install/doctor 命令 | 首发频率低，README 写清楚部署 SOP 即可 | — |

## 四、执行安排

- **总量**：约 +900 行（含测试），全部集中在 client 端 + 一个服务端小校验 + C# SDK 两个可选方法；
- **周期**：单人 1.5~2 周（对比上一版 6~8 周）；
- **顺序**：5（apply 挪复制，独立且收益最大）→ 4/6（同在 download_update.go，一起做）→ 1/2/3（UI 一批）→ 7/8（收尾）。每件独立 commit，走 AGENTS.md 审查流程；
- **文档**：完成 4 时顺手把 stdout JSON 字段说明补进 README（一页）。

## 五、决策点（只剩 3 个）

1. 倒计时时长 10s 还是 30s？（建议 10s）

   回答：10s

2. 服务端防倒退要不要留 `--allow-downgrade` 例外口子？（建议留，发布侧偶尔真需要回退）

   回答：不需要

3. 第 5 条 apply 瘦身：复制挪到 download 后，apply 里的复制逻辑**保留当兜底**（推荐，多一层保险、零成本）还是删掉？（建议保留）

   回答：删掉
