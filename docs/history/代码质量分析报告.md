## 0. 关键约束（分析前提）

> ⚠️ **以下约束直接影响所有改进建议的可行性，必须优先考虑**

| 模块 | 运行环境 | 框架/版本 | 特殊限制 |
|------|---------|-----------|---------|
| **aly-client/** | Windows XP 及以上 | **Go 1.10**（GOPATH 模式，非 Module） | 不能用 Go 1.11+ 的任何新特性（module、泛型、errors.Is、io.ReadAll、os.ReadFile 等） |
| **aly-client-sdk/** | .NET Framework 4.0+ / .NET Standard 2.0 | C# 5.0 | 不能用 C# 6.0+ 的高级语法；需支持自更新（自我替换） |
| **server/** | 现代 Linux/Windows | Go 1.25（Module 模式） | 无特殊限制 |
| **publish-cli/** | 现代 Windows/Linux | Go 1.25（Module 模式） | 无特殊限制 |
| **publish-gui/** | Windows 及以上 | .NET 8 + Avalonia 11.3 | 无特殊限制 |

**核心影响**：
1. **Go 代码无法三端共享** — aly-client 的 Go 1.10 + GOPATH 模式与另外两端的 Go 1.25 + Module 模式差异太大，强行共享会拖累现代端
2. **C# SDK 无法使用现代语法** — 必须兼容 .NET 4.0，很多 C# 6.0+ 的语法糖和 API 不能用
3. **aly-client 是所有约束的瓶颈** — 任何涉及跨端共享的方案都要先问「Go 1.10 能跑吗？」

## 二、高优先级问题（必须改进）

### 2.1 publish-gui: ViewModel 未使用 [RelayCommand] 源生成器

**问题**：项目引用了 CommunityToolkit.Mvvm 8.4.0，但所有命令都是手动 `new AsyncRelayCommand(...)`，完全浪费了源生成器能力。每个 ViewModel 构造函数里有 5-15 个命令的手动 new，`OnIsBusyChanged` 里还要手动调用 `NotifyCanExecuteChanged`。

**涉及文件**：
- [ProjectTabViewModel.cs#L72-L111](file:///e:/Project2026/aly/publish/publish-gui/src/AlyPublish/ViewModels/ProjectTabViewModel.cs#L72-L111) — 8 个命令
- [EditProjectDialogViewModel.cs#L63-L76](file:///e:/Project2026/aly/publish/publish-gui/src/AlyPublish/ViewModels/EditProjectDialogViewModel.cs#L63-L76) — 13 个命令
- [MainWindowViewModel.cs](file:///e:/Project2026/aly/publish/publish-gui/src/AlyPublish/ViewModels/MainWindowViewModel.cs) — 多个命令
- 其他 3 个 DialogViewModel — 每个 2-3 个命令

**改进方向**：
```csharp
// 现在的写法
public IAsyncRelayCommand RefreshStatusCommand { get; }

public ProjectTabViewModel(...)
{
    RefreshStatusCommand = new AsyncRelayCommand(RefreshStatusAsync, () => !IsBusy);
}

partial void OnIsBusyChanged(bool value)
{
    RefreshStatusCommand.NotifyCanExecuteChanged();
    // ... 还有 N 个
}

// 建议的写法
[RelayCommand(CanExecute = nameof(CanRefresh))]
private async Task RefreshStatusAsync() { ... }

private bool CanRefresh => !IsBusy;
```

**收益**：ViewModel 代码量减少 30%+，消除 `OnIsBusyChanged` 里的 N 个 Notify 调用。

**优先级**：🔴 高（纯收益，零风险，不改变任何行为）

### 3.3 aly-client-sdk: AlyApi 类大而全，Process 启动代码重复

**问题**：
- `RunAsync<T>`、`DownloadUpdateAsync`、`RunAsyncAlone` 三个方法都手动构建 `ProcessStartInfo`，重复代码多
- `DownloadUpdateAsync` 里有一整套进度解析逻辑，与 `RunAsync` 完全不同
- 类声明为 `public class AlyApi`（非 `static class`），但所有成员都是 static，建议显式标记为 `static class` 防止误实例化

[AlyApi.cs](file:///e:/Project2026/aly/client/aly-client-sdk/AlyClient.CSharpSDK/AlyClient.CSharpSDK/AlyApi.cs)

**额外发现**：`DownloadUpdateAsync` 中 `process.Exited += (s, e) => cts.Cancel();`（L51）但未设置 `process.EnableRaisingEvents = true`，Exited 事件**永远不会触发**，cts.Cancel 永远不会调用。当前能工作是因为进程退出后 `ReadLine()` 返回 null 退出循环，但 Exited 订阅是死代码，且若进程变成僵尸状态会导致 ReadLine 无限阻塞。

**约束说明**：
- SDK 需要兼容 **.NET Framework 4.0**，很多现代模式用不了
- 全静态方法的设计是为了调用简单（`AlyApi.CheckUpdateAsync(...)`），符合 SDK 的易用性目标

**改进方向**：
- 提取私有方法 `BuildProcessStartInfo(exePath, args, redirectOutput)` — 这个可以做，不影响外部 API
- 提取 `ProcessRunner` 类封装进程启动/读取逻辑 — 这个可以做，内部用，外部 API 不变
- 删除冗余的 `process.Exited` 订阅，或补上 `EnableRaisingEvents = true`
- 将 `AlyApi` 标记为 `static class` — 可以做，向调用方明确意图
- 将 `AlyApi` 改为实例类 — **不建议**，会破坏现有调用方式

**优先级**：🟡 中（内部去重 + 修复死代码）

### 3.4 aly-client-sdk: AlyUpdateClient 构造函数里做了太多事

**问题**：构造函数里直接：
1. 调用 `CheckSelfUpdateAsync(...).Result`（同步阻塞，可能死锁）
2. 复制文件
3. 启动后台线程 `MainLoop`

[AlyUpdateClient.cs#L47-L66](file:///e:/Project2026/aly/client/aly-client-sdk/AlyClient.CSharpSDK/AlyClient.CSharpSDK/AlyUpdateClient.cs#L47-L66)

**风险**：
- `.Result` 在 UI 线程可能造成死锁
- 构造函数不应启动后台线程（违反"构造函数只做初始化"原则）
- 调用者无法控制何时开始检查更新

**约束说明**：
- SDK 需要兼容 **.NET Framework 4.0**，很多现代模式（如 `IHostedService`、`IAsyncDisposable`）用不了
- SDK 需要**自更新**（自己替换自己），所以在构造函数里就开始更新是有业务原因的 —— 确保最早时机检查更新
- 调用方式是 `new AlyUpdateClient(...)` 一行搞定，简单粗暴但符合 SDK 的易用性设计

**权衡说明**：
- 当前设计的**合理性**：自更新 SDK 的核心诉求就是"尽可能早地、静默地完成自更新"，构造函数里做是最直接的方式
- 当前设计的**问题**：`.Result` 阻塞调用在 UI 线程有死锁风险
- **更稳妥的改进**：不是把逻辑挪出构造函数（那样调用者可能忘记调用 Start），而是**用线程池线程跑自更新**，避免阻塞调用者的线程

**改进方向**：
1. 把自更新检查放到 `ThreadPool.QueueUserWorkItem` 里，构造函数立即返回，不阻塞调用者
2. 增加 `IsReady` 事件或回调，通知调用者自更新完成
3. 保留"构造即启动"的易用性，同时避免死锁风险

**优先级**：🟡 中（有设计原因，但 .Result 死锁风险需要关注）

### 3.6 server: UploadChunkComplete 句柄管理（修正原报告）

**原报告说法**：destFile 没关闭、chunkFile 没关闭 → 句柄泄漏。

**实际验证**（[file_upload_controller.go#L220-L241](file:///e:/Project2026/aly/server/controllers/file_upload_controller.go#L220-L241)）：
- `destFile` 有 `defer destFile.Close()`（L226），函数返回时会关闭 ✓
- `chunkFile` 在成功路径 L240 `chunkFile.Close()`、io.Copy 失败路径 L236 `chunkFile.Close()` 都调用了 ✓
- `os.Open` 失败路径：chunkFile 为 nil，不需要 Close ✓

**结论**：原报告关于"句柄泄漏"的描述是**错误的**。当前代码在所有正常路径都正确关闭了句柄。

**仍可改进**：chunkFile 用手动 Close 而非 defer，如果未来在 io.Copy 之前插入新代码可能遗漏。建议改为 `defer chunkFile.Close()` 模式，更健壮。但这不是 bug，是风格改进。

**优先级**：🟢 低（风格改进，非 bug）

## 七、简洁 vs 设计模式的权衡建议

**当前状态**：项目整体偏向"简洁实用"，在很多地方做出了务实的权衡（比如 ViewModel 直接引用 View、SDK 构造函数里启动更新、Go 1.10 手写辅助函数）。**这是对的**。

**推荐策略**：

1. **消除「模块内」的重复是第一优先级**
   - 同一个模块内的方法重复（如 EditProjectDialogViewModel 的 8 个 Add/Remove、ProcessService 的两个 Run 方法）—— 这些没有版本约束，直接改
   - 跨端的重复——受 Go 1.10 / .NET 4.0 约束，接受它，用测试保证行为一致

2. **源生成器这类零成本的优化，直接用**
   - `[RelayCommand]` 没有任何副作用，纯收益，不用白不用

3. **设计模式只在确实需要时引入**
   - 比如 IDialogService，当前 4 个对话框，没必要
   - 等对话框超过 10+、或者需要写单元测试了，再重构不迟
   - **不要为了"符合 MVVM"而过度设计**

4. **不要为了"架构优雅"而强行跨端共享**
   - Go 1.10 + GOPATH vs Go 1.25 + Module，这道鸿沟太大了
   - 强行共享的结果就是：现代端被老版本拖累，代码更复杂，还容易出 bug
   - 用测试 + 文档保证行为一致，比共享代码更可靠

5. **保持当前的"够用就好"风格，聚焦于减少重复和魔法字符串**
   - 这是性价比最高的改进方向
   - 核心原则：**简单的代码 = 更少的 bug = 更容易维护**

**一句话总结**：代码整体质量不错，核心问题是「模块内重复」和「魔法字符串」，把这两个解决了，项目质量会上一个台阶。跨端的重复是约束下的必然代价，不要强求。
